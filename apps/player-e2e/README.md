# player-e2e

End-to-end tests for the core flow: open a game, run actions, save/load, reopen from the shelf. They are written as [Serenity/JS](https://serenity-js.org) Screenplay scenarios that run unchanged on both targets.

- Web: Playwright Test (`targets/web/`), runs against the production build of `apps/player`.
- Desktop: WebdriverIO + mocha + `tauri-driver` (`targets/desktop/`), runs against the debug Tauri binary.
- Test pack: `fixtures/game.cfg` lists two games, `e2e-game/e2e-game.qsps` ("E2E game": a tiny QSP game with a `start` and a `room` location, a counter, Save and Load actions) and `second/game.qsps` ("Second game"). `fixtures/test-pack.ts` (`TEST_PACK`) holds the config path, the pack zip path and the shelf titles; `fixtures/e2e-game.ts` holds the first game's file path and the texts it writes. `e2e-game.qsps` sits in its own folder, away from `game.cfg`: the desktop player titles a single game file from a `game.cfg` next to it, and a single-file open must show the file name (`e2e-game.qsps`) on both targets. Each scenario starts with an empty shelf and no saves. On desktop the app is always launched with the pack: `tauri-driver` starts it with `game.cfg` as its argument. On web a scenario loads the pack only when it calls `LoadTestPack()` (directly or through `OpenFixture()`): `targets/web/global-setup.ts` zips `game.cfg` and the games it lists into `artifacts/test-pack.zip`, and the scenario uploads it through the Open game input. Every scenario does so except "opening a game file", which on web starts from an empty shelf. The saves fixture (`fixtures/saves/saves.qsps`, packed as `artifacts/fixtures/saves.zip`; `fixtures/saves-game.ts` holds its path and texts) is not in the pack: saves scenarios open it with `OpenGameFile` (`OpenSavesFixture()`).

The panels fixture (`fixtures/panels/`, packed as `artifacts/fixtures/panels.zip`, "Panels game"; `fixtures/panels-game.ts` holds its action names and texts) is not in the pack either: scenarios open it with `OpenGameFile` (`OpenPanelsFixture()`). It is a game with a `game.cfg` and one room per feature: `start` (the hub), stats, objects, the command line, action keys (`keys`, `single`), system commands (`system`), lifecycle (`life`) and the timer (`counter`). `start` runs `inclib 'qspider'` (the built-in module, for `qspider_event`, `qspider_restart` and the other `qspider.*` commands) and `inclib 'panels-lib.qsps'` (a real library loaded from the archive), and its `game.cfg` has a `[game.hotkeys]` entry (`k` runs `hotkey_loc`). Keep a location to at most 8 actions: Serenity `isVisible()` treats an action scrolled out of view as invisible, so a longer list makes later actions unclickable.

The theme fixtures (`fixtures/themes-game.ts` holds their paths, titles, texts and the theme aliases) are built by `fixtures/build-fixtures.ts` into `artifacts/fixtures/` and opened with `OpenGameFile`, not through the pack:

- `aero-game/` ("Aero game", `mode = "aero"`): a message and a next location.
- `themed-game/` ("Themed game"): a game theme made of `e2e-theme.html`, `e2e-theme.css` and `e2e-theme.js` (`defaultTheme = "e2e-custom"`; the theme writes `data-qa` marks of its own, and has a layout-level `qsp-layer` outside the main content). Its actions switch themes at runtime (`qspider_change_theme`, including an unknown name).
- `missing-theme/`: two zips (`missing-aero.cfg`, `missing-classic.cfg`) whose `defaultTheme` names no theme, in Aero and in classic mode.
- `gui-cfg-game/` ("GUI cfg game"): a game with a `qspgui.cfg` that puts the stats panel in the left dock, plus a control zip of the same game without the cfg.
- `look-game/` ("Look game"): the look-variable game (start, dialogs, formats, effects), packed once in Aero and once in classic mode; `fixtures/look-game.ts` holds its markers and the frozen tables of CSS custom properties its `Set vars` action produces. Its PNGs are generated by build-fixtures.
- The e2e game in theme variants (`e2e-game-aero.zip`, `e2e-game-custom.zip`): the same `e2e-game.qsps` with an authored `game.cfg` that selects Aero, or the themed game's theme files. `CORE_THEME_VARIANTS` points at them.

### Product behaviour the suite relies on

The desktop player opens what it is launched with, what is dropped on it and what is picked with Open game through the same decision as the web player's Open game (`addImported`, `libs/game-shelf/src/add-imported.ts`):

- more than one game imported (a `game.cfg` listing several, or a multi-game `.zip`): all go on the shelf, overwriting entries with the same id, with the notice `{{ count }} games added to shelf`, and none starts;
- exactly one: it is added (overwriting) and starts;
- none: an error.

This changed desktop behaviour on this branch: launching with, or dropping, a multi-game `.zip` used to start its first game; it now only shelves the games. On desktop, only a file named `game.cfg` (any case) is a game config; any other `.cfg` is an error ("Only game.cfg is supported …"), not a single-file import, and a `game.cfg` that lists the same `id` twice is an error.

## Layout

```
apps/player-e2e/
  scenarios/            the tests, one file per feature (*.scenario.ts); run on both targets
  screenplay/
    <area>/             elements.ts, tasks.ts, checks.ts (as needed) for one place in the UI
      shelf/ game/ pause/ saves/ stats/ objects/ cmd/ content/ view/ wait/ msg/ input/ menu/
    common/             elements and checks used by more than one area
    support/            shared primitives (below)
  targets/
    web/                playwright.config.ts, global-setup (builds the pack zip), Cast, OperateWebPlayer, scenario shim
    desktop/            wdio.conf.ts, Cast, OperateDesktopPlayer, native-dialog, atspi/ (dialog.py, with-a11y-bus.sh),
                        run-desktop-e2e.mjs, private-session, scenario shim, fresh-app, prereqs
  fixtures/             the test pack (game.cfg, test-pack.ts), its games and their constants
```

`screenplay/support/` holds: `operate-player.ts` (the abstract ability), `scenario.ts` (the `scenario()` shim), `see-eventually.ts`, `presence.ts` (`waitUntilPresent`, `waitUntilAbsent`, `ClickWhenPresent`, `PresenceOf`, `AbsenceOf`, `TextNow`, `isShown`, `textIfPresent`), `polling.ts` (`pollUntil`, the fixed-interval loop under them), `element-errors.ts` (which driver errors mean "element missing"), `visible.ts`, `hover.ts` (`Hover`, `MoveAway`), `type-into.ts` (`TypeInto`), `timeouts.ts`, `scenario-location.ts`, `timeout-report.ts` (the timeout tail shared by `seeEventually` and the page-script checks: one strict `Ensure.that` reports Expected/Received, with the last error appended), `see-script-eventually.ts` (the polling check behind the page-script checks), `describe-names.ts` (names in check descriptions), `page-script.ts`, `sound-state.ts` (sound probes, below), `image-loaded.ts` (`SeeImageLoaded`), `game-resources.ts` (`SeeGameResourceCount`), `proxy.ts` (`SeeProxied`) and `page-clock.ts`. Add to it only with a reason.

- `page-script.ts` is the one place that runs script in the page, and it is read-only: a scenario picks a named probe (`SeePageProbe`: `fullscreenElementMarker`, `pageClock`) and cannot pass code. `RecordWindowEvents(type)` starts a recording of window events and `SeeRecordedEvent(type, detail)` checks it. `RecordWindowEvents` clears what was recorded on every call, so call it right before the trigger, and again after a reload (the recorder lives in the page; a check without it fails at once). Details are JSON copies, so both targets read the same data (`NaN` and `undefined` read as `null`).
- Sound (`support/sound-state.ts`): `SoundState(srcSuffix)` reads `{ playing, volume }` of the first Howl whose source ends with the suffix (`null` when the game has not created one), `AudioState()` reads the master `{ muted, volume }`, and `SeeSoundState(suffix, expected)` / `SeeAudioState(expected)` check them. A sound that `CLOSE` stopped stays registered as `playing: false`, so `null` only means it was never played. The suffix is regex-validated (letters, digits, `_ . / space -`) and goes only to `endsWith`. `playing` reads Howler's own flag, which does not tell web audio from the HTML5 fallback Howler switches to when its XHR fails.
  - Sound assertions: a sound line in the game writes `str(ISPLAY(...))` in the same action, so the text shows what the game sees and the probe shows what Howler does; check both. `SeeSoundWebAudio(suffix, expected)` reads the `webAudio` flag, which tells web audio from the HTML5 fallback. Closed sounds stay registered (`playing: false`) until the game stops.
- Images: `SeeImageLoaded(target, width)` (`support/image-loaded.ts`) reads `naturalWidth` of the first `<img>` with that `data-qsp` / `data-qa` once it has finished loading (0 = failed); each fixture image has its own width, so a wrong file also fails.
- `game-resources.ts`: `SeeGameResourceCount(n)` counts the elements the player added for the running game's `game.cfg` resources (`[data-qspider-resource]`).
- Computed styles (look variables): `CssValues(target, names)` reads trimmed `getComputedStyle(...).getPropertyValue` for each name, `SeeCssValues(target, { name: value })` checks exact values and `SeeCssValue(target, name, expectation)` any string expectation. `target` is `{ root: true }` (`qsp-game-root`), `{ qsp }` or `{ qa }` (first element with that marker). The marker is regex-validated (`[a-z0-9-]+`) before it builds a selector; an absent target reads `null`, and a missing property reads `''`. Both targets return the same strings (e.g. `#000000`, `12px`, `black`, `1`), so a table compares exact text.
- `page-clock.ts`: `PageClockAdvanced(ms)` waits on the page's own clock. It is the single documented exception to "no fixed sleeps", for elapsed time that has no UI event. The only allowed use is the counter "does not run while a dialog / the pause screen is open" checks (`counter.scenario.ts`), with ms = 5 x the timer interval. Any other use needs maintainer approval.

### Resources and sound fixtures

- `resources-game/` ("Resources game", `fixtures/resources-game.ts`): packed as a zip and also served as a plain folder (the web plain-URL route; the desktop plain-folder scenario). One location per feature: every `<img>` / CSS-variable / view / object / menu path spelling, `game.cfg` resources (two styles, two scripts, a font), a variant zip with a missing script and style, and a sound location whose lines write `ISPLAY`. The PNG, SVG, WAV and TTF files are generated by `build-fixtures.ts` (`resource-assets.ts`); the wavs last 20 s so no sound ends by itself during a scenario.
- Asset server (`fixtures/asset-server.ts`): serves the files the game names by absolute URL (image, sound, text read by a game script's XHR) from `127.0.0.1:47631`, with `Access-Control-Allow-Origin: *`. The port is fixed because the game spells the URL. Both targets start it once per run: the web `global-setup.ts` and the desktop `wdio.conf.ts` `onPrepare`. A busy port fails the run loudly (a thrown error on web, a `SevereServiceError` on desktop, since WDIO ignores other `onPrepare` errors).

### Desktop isolation

**Never run `wdio` directly for desktop** (`wdio run apps/player-e2e/targets/desktop/wdio.conf.ts`): the app would open on your real display, GTK would write your real dconf, and the dialog driver would talk to your real accessibility bus. Use `pnpm e2e:desktop`, or `node apps/player-e2e/targets/desktop/run-desktop-e2e.mjs [wdio args]` after a build. On Linux, `wdio.conf.ts` (`onPrepare`, before launching anything), `atspi/dialog.py` and `atspi/with-a11y-bus.sh` all refuse to run (`targets/desktop/private-session.ts` for the first) unless `QSPIDER_E2E_PRIVATE_SESSION=1` is set and `DBUS_SESSION_BUS_ADDRESS` is set and is not the desktop bus (`/run/user/<uid>/bus`).

`targets/desktop/wdio.conf.ts` starts one `tauri-driver` per run, with its own temporary `XDG_DATA_HOME`/`XDG_CONFIG_HOME`/`XDG_CACHE_HOME`. Before each scenario, `targets/desktop/fresh-app.ts` (called by the desktop scenario shim) ends the WebDriver session, waits (via `/proc`) until the app and its WebKit processes have exited, empties those dirs and starts a new session; `tauri-driver` then launches a new app process with the pack's `game.cfg` as its argument. This relies on XDG dirs and `/proc`, so it is Linux-only; on other platforms every scenario fails at its start, in the restart that runs inside each test (`targets/desktop/scenario.ts`).

The asset server (above) is started by `wdio.conf.ts` inside this private session and binds loopback only, so it needs no network access beyond the machine. The session also drops the PulseAudio and PipeWire routes (`PULSE_SERVER`, `PIPEWIRE_REMOTE`, and `XDG_RUNTIME_DIR` is private). Direct ALSA access is not blocked, so the desktop sound scenarios assert Howler's state, not what is heard.

`restartAppKeepingData()` (same file) is the same restart without emptying the dirs: the same isolation, the run's private dirs only, with the app data kept. It is for persistence scenarios (`RestartPlayer()`, below).

## Rules

Scenarios are written under these rules. `nx lint player-e2e` enforces the mechanical ones (`eslint.config.js`), all as errors:

- `scenarios/**`: no static imports from Playwright, WebdriverIO, `@wdio/*`, `@serenity-js/playwright*`, `@serenity-js/webdriverio`, `@serenity-js/web` or `targets/**`.
- `screenplay/**`: no static imports from `targets/**`, Playwright, WebdriverIO or `@wdio/*`. `support/scenario.ts` may reach `targets/` (it loads the target's scenario shim).
- No dynamic `import()` anywhere in `apps/player-e2e`, so the import bans cannot be bypassed. The one exception is `screenplay/support/scenario.ts`, the shim loader above.
- `Ensure` is imported only in `screenplay/support/`; the ban covers `scenarios/`, `targets/` and the rest of `screenplay/`, `checks.ts` included (checks go through `seeEventually`).
- `isPresent` (from `@serenity-js/assertions` or `@serenity-js/web`) is imported only in `screenplay/support/`: on desktop it throws instead of answering false (see "Reading and waiting").
- `ExecuteScript` and `LastScriptExecution` (from `@serenity-js/web`) are imported only in `screenplay/support/page-script.ts`, and a `.executeScript(...)` call fails lint everywhere else. That file exposes only read-only named probes (`SeePageProbe`), computed-style reads (`CssValues`, `SeeCssValues`, `SeeCssValue`), sound probes and an event recorder (`RecordWindowEvents`, `SeeRecordedEvent`), never an arbitrary-code API.
- `scriptResult` (`page-script.ts`) runs any function in the page, so it is exported only for the probe files in `screenplay/support/` (`sound-state.ts`, `image-loaded.ts`, `game-resources.ts`) and `no-restricted-imports` bans importing it anywhere outside `screenplay/support/`. The contract for a probe file: self-contained functions (no closures, they are serialised into the page), read-only (no writes to the page), returning plain data.
- `tasks.ts` may import checks only from `common/checks.ts` (the fail-fast guards such as `SeeGameStarted`); an import of any other `checks` module fails lint.
- `By` is imported only in `elements.ts` and `screenplay/support/`; the ban covers `scenarios/`, `targets/` and the rest of `screenplay/`.
- In `elements.ts`, a string or template literal passed straight to `By.css` must contain `[data-qsp`, `[data-qa` or `[role=`. Other `By` forms (`By.xpath`, `By.id`, `By.cssContainingText`, …) and non-literal arguments are not checked; reviewers cover those.
- No fixed sleeps: a call written as `Wait.for(...)` fails lint anywhere (an aliased `Wait` is not caught).
- `screenplay/**` files have at most 150 lines.
- `@typescript-eslint/no-floating-promises` and `no-misused-promises` (type-aware) everywhere, so an `attemptsTo(...)` without `await` fails lint.

The rest (naming, where an element or task belongs, no text or class lookups beyond what the selector check catches) is up to review.

### Where things go

An **area** is a place in the UI where the player can be: a screen (shelf, game) or an overlay on it (pause menu, saves panel). Test: can you name where the player is looking with one noun?

| What     | Where                                                                                                                             |
| -------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Area     | `screenplay/<area>/`, with `elements.ts` (definitions only, the only file with selectors), `tasks.ts`, `checks.ts` as needed      |
| Element  | In the area where it is visible; visible in more than one area: `screenplay/common/`                                              |
| Task     | In the area where the player starts it (`ReturnToShelf` starts in the game, so it is in `game/`, though it passes the pause menu) |
| Check    | In the area that shows what is checked                                                                                            |
| New area | When a new screen or overlay appears, or a file passes about 150 lines and a natural sub-place can be split out                   |
| Never    | An area per feature. "Quick save" is a scenario that uses tasks from the places it touches                                        |

An area has only the files it needs: `pause/` has only `elements.ts`.

- `elements.ts`: `PageElement` / `PageElements` and nothing else.
- `tasks.ts`: `Task`s and `Interaction`s (what the player does). Never calls `Ensure`. May compose only the fail-fast guards in `common/checks.ts` (`OpenFixture` uses `SeeGameStarted` to fail fast on an error alert); area checks belong in scenarios. May wait for the UI to settle after its own action.
- `checks.ts`: what the player expects to see, always through `seeEventually` (never `Ensure` directly).
- Scenarios contain only tasks, checks and constants: no selectors, no `Ensure`, no framework or `targets/` imports.

### Naming

- Elements are nouns: `Shelf`, `MainText`, `RunLink`.
- Tasks are verb phrases: `OpenFromShelf`, `ReturnToShelf`, `OpenGameFile`.
- Checks start with `See`: `SeeMainText`, `SeeShelfTitles`, `SeeSlotEmpty`.
- Scenario files are named for the feature: `saves.scenario.ts`. Titles state behaviour: `loading a save restores the saved state`.

### Locating elements

Find controls and panels only by:

- `data-qsp*` markers, the theme contract: the renderer's markers on `qsp-*` building blocks;
- ARIA roles;
- Aero-only `data-qsp` markers: `overlay` (the dialog shade), `menu-anchor` (the context-menu anchor) and `newloc-effect` (the new-location transition wrapper, rendered only while an effect is set);
- `data-qa` hooks, **for app-shell UI only** (the shelf, the Open game button and the toasts, which are not rendered from theme templates): `game-shelf` (its non-visible `data-pending-writes` is the number of shelf changes not yet written to storage) and `game-shelf-empty` (`libs/game-shelf`, `game-shelf.tsx`), `game-card` (on the card root), `game-title` and `game-run` (`game-card.tsx`), `error-alert` (`error-alert.tsx`), `notice-toast` (`notice-toast.tsx`, the transient notice), `game-remove` (`game-card.tsx`, the card's remove button), `locale-select` (`locale-selector.tsx`; the trigger's `data-value` is the current language code) and `locale-select-option` (its options, rendered while it is open; `data-value` is the option's language code), `theme-switch` (`qspider-theme-switch.tsx`), `startup-finished` (`startup-marker.tsx` in `libs/renderer`, a hidden marker, below) and `open-game` (`apps/player-desktop/src/app/open-game-button.tsx`, desktop only). These are all the app-shell `data-qa` hooks that exist. The player theme is read from `[data-qa="player-body"]` (the `body`, marked by `initTheme()` and by the `playerTheme$` subscriber; not set in the standalone build) attribute `data-player-theme` (`light` or `dark`, from `libs/game-state/src/player-theme.ts`). The pause screen's language select is `[data-qsp="locale-select"]` (given by `useAttributes`). Game-authored markup passes through the sanitizer with its own `data-qa`, so a hook in a theme or fixture file (e.g. `e2e-theme-chrome`, `e2e-theme-script` in `fixtures/themed-game/e2e-theme.html`) is not an app-shell hook and is not in this list; such hooks are located from `screenplay/themes/<theme>/`. The web player's Open game control is the `#openGame` file input, which only the web target's `openGameFile` touches.

Never by visible text, CSS class, nesting or layout: themes and translations change all of them. Text is only for checking content the game writes (`ROOM counter=1`) or that the scenario controls (fixture titles). If a control has no marker or role, add a `data-qsp` marker in the renderer (or a `data-qa` hook in app-shell UI); do not use a fragile selector. Lookups that can match hidden duplicates go through `visible()`.

### Reading and waiting

- **One check primitive.** Every check is `seeEventually(element, question, expectation, description)`: it polls until the element is present and the question meets the expectation. A read error during polling means "not yet". On timeout one strict `Ensure.that` reports Expected/Received, with the last read error appended. The one exception: `SeeAppClosed` (standalone, desktop) checks a process, not an element, so it polls `OperatePlayer.appRunning` with `pollUntil`.
- **The desktop trap.** On desktop, WebKitWebDriver answers a read of a missing element with a raw "no such element" (it prints as `[object Object]`), and Serenity's `isPresent()`, `Wait.until` and `Ensure.eventually` rethrow it instead of retrying. So an element that has not rendered yet, or is re-rendering, fails a plain read at once.
- **Presence helpers.** Checks read only through `seeEventually`. Tasks wait and click through `support/presence.ts`: `waitUntilPresent` (any read error means "not yet"), `ClickWhenPresent` (retries the click while the element is missing, up to the timeout), `waitUntilAbsent` (only a missing element counts as gone; other errors surface), `TextNow`, `isShown`, `textIfPresent`. Lint bans `Ensure` and `isPresent` outside `support/`; other reads (`Text.of`, `Attribute`, …) outside these helpers are up to review.
- **Emptiness needs a settled anchor.** A check that something is empty or absent (empty shelf, empty save slot) passes as soon as the UI is briefly empty, and `games$` and the save slots load asynchronously, so they start empty. Before such a check, check a settled anchor: something that shows only once loading has finished, or a non-empty state seen earlier in the same scenario. Neither the shelf's empty notice nor a slot's `data-save-empty` marker is one (both show while loading), so `SeeShelfTitles([])` and `SeeSlotEmpty` in `core-flow` show the expected start state but cannot prove that no game or save was left over; a real guard needs a loaded marker in the UI first. Eventual checks in general only wait for a match: they do not prove the state stays that way, so they do not catch leftovers or duplicates that appear after the match.
  - "No game started" has a settled anchor on desktop: `[data-qa="startup-finished"]` (`StartupMarker`, rendered from `startupFinished$` in `libs/game-state/src/init.ts`, set at the end of the web, desktop and standalone players' `init()`, after the desktop launch's start decision; `SeeStartupFinished` in `common/checks.ts`). On desktop the start-up shows the shelf first and starts a launched game only later, so a shelf check alone could pass before the game replaces it. "loading a game config adds all its games to the shelf without starting one" checks the marker first, then the shelf with exactly the pack's titles: a game started at launch would have replaced the shelf by then, so on desktop this exact check proves that no game started.
  - Both targets make that start decision with the same shared code, `addImported` (`libs/game-shelf/src/add-imported.ts`, unit-tested in `add-imported.spec.ts`). Desktop proves "no game started" through the startup marker as above. On web the pack is uploaded after startup, so the marker says nothing about the upload: web exercises the same code but checks only the shelf titles, an eventual check that waits for the import.
  - "opening a game file" checks the marker before `OpenGameFile`, on both targets, so the Open game click does not race `init()`.
- **Timeouts.** `INTERACTION_TIMEOUT` is 15s (`support/timeouts.ts`), set as Serenity's `interactionTimeout` by both target configs. The support helpers poll every 250ms (`POLLING_INTERVAL`), not with Serenity's exponential backoff, so a failing check gives up after about 15s. The per-scenario timeout (Playwright `timeout`, mocha `timeout`) is 45s: the scenario's steps (and, on desktop, the app restart) plus one failing check.
- **No fixed sleeps** (`Wait.for`) and **no test-level retries** (Playwright `retries: 0`, mocha `retries: 0`). The one sleep exception is `PageClockAdvanced` (see `page-clock.ts` above). The one retry exception is WDIO `specFileRetries: 2` on desktop: an intrinsic app-relaunch hang (#167) is absorbed by retrying the spec file in a fresh worker (see the comment in `wdio.conf.ts`).
- Every `actor.attemptsTo(...)` is awaited; a missing `await` lets a scenario pass without checking anything.
- A game that fails to open fails the scenario within seconds with the player's error text (`SeeGameStarted` in `common/checks.ts`).

### Target differences: `OperatePlayer`

`support/operate-player.ts` defines `abstract class OperatePlayer extends Ability` with one method per capability that differs by target (`startPlayer`, `loadTestPack`, `openGameFile`, `dropGameFile`, `restartPlayer`, `openGameUrl`, `delayRequests`, `routeThroughProxy`), and one `Interaction` per capability (`StartPlayer()`, `LoadTestPack()`, `OpenGameFile(path)`, `DropGameFile(path)`, `RestartPlayer()`, `OpenGameUrl(url)`, `DelayRequests(suffix, ms)`, `RouteThroughProxy(origin)`). Shared code only calls `OperatePlayer.as(actor)`. There is one subclass per target: `targets/web/operate-web-player.ts` and `targets/desktop/operate-desktop-player.ts`. Each target's Cast (`targets/<target>/cast.ts`) gives every actor its browsing ability plus its subclass. A new method does not compile until both targets implement it.

- `startPlayer`: web navigates to `/`; desktop does nothing (the app is already launched).
- `loadTestPack` (`LoadTestPack()`): web uploads `TEST_PACK.zipPath` through `openGameFile`; desktop does nothing, because `tauri-driver` launches the app with `TEST_PACK.configPath` as its argument (`wdio.conf.ts`), once per app launch.
- `restartPlayer` (`RestartPlayer()`): ends the player and starts it again with its stored data (shelf, saves) kept. Web navigates the page to `/` again in the same browser context (a full page load, so `init()` reads IndexedDB back); desktop calls `restartAppKeepingData()`, so the new app process is launched with the pack again. Check `SeeStartupFinished()` after it.
  - Persistence scenarios that remove or keep a game cannot use a pack game on desktop: the relaunch imports the pack again and puts it back. They open a game with `OpenGameFile` (`shelf.scenario.ts` uses the archives and saves fixtures) and assert that one.
- `openGameFile(path)` (`OpenGameFile(path)`): starts on the shelf and opens the file at `path` through the player's Open game control. Web sets the file on the `#openGame` input through the native Playwright page (Serenity's web API has no upload). Desktop clicks the `open-game` button and then drives the native GTK file chooser from `targets/desktop/native-dialog.ts`, which runs `atspi/dialog.py` (below).

- `delayRequests` (`DelayRequests(pathSuffix, ms)`) and `routeThroughProxy` (`RouteThroughProxy(origin)`): web only (Playwright network routing); desktop throws, so use them only in `scenario.webOnly` variants. `DelayRequests` holds back requests ending with the suffix, to test load order. It routes on the browser context, so it also holds the service worker's own requests (its script included: a page route never sees them); a request the worker answers from IndexedDB never reaches the network, so it cannot be held. `RouteThroughProxy` makes the origin unreachable for the browser except through the CORS proxy, so the game must be fetched via the fallback; call it after `StartPlayer()`. `SeeProxied(url)` (`support/proxy.ts`) checks that the proxy was asked for a URL (the list of recorded original URLs, `proxiedUrls`, contains it); desktop throws.

- `emulateColorScheme` (`EmulateColorScheme('light' | 'dark')`): web only (Playwright's `emulateMedia`, kept across page reloads); desktop throws, so use it only in `scenario.webOnly` variants. Call it before `StartPlayer()` / `RestartPlayer()` to set the OS colour scheme the player starts with.

- `appRunning` (read by `SeeAppClosed()`, `screenplay/standalone/checks.ts`): desktop only, whether an app process still runs under `tauri-driver` (`appRunning()` in `targets/desktop/fresh-app.ts`); web throws. It proves a quit closed the app: a closed window can no longer answer the page. The next scenario's restart tolerates an app that already exited (its last known processes are gone), and still fails with "No app process found" when no app was ever launched. Click the quitting action with `ClickActionClosingTheApp(label)` (`screenplay/standalone/tasks.ts`): the app can exit before the click is answered, and only that ended-session error is accepted (`SeeAppClosed` then proves the app is gone). After such a scenario the desktop actor skips discarding its windows when no app runs (`targets/desktop/cast.ts`), since the session is dead.

Windows later uses UI Automation for the native dialog, behind the same `openGameFile`: no scenario changes.

#### The native dialog (desktop)

The file chooser is a window outside the webview, so WebDriver cannot reach it. `atspi/dialog.py` drives it through AT-SPI, the Linux accessibility API, with no keystrokes and no dependence on the UI language: it waits for the chooser (role `FILE_CHOOSER` in the `qspider` app), runs its `show_location` action to reveal the location entry, sets the path through the entry's EditableText, and activates the entry (Return). Failures exit 1 with a message that `native-dialog.ts` rethrows as `Native file dialog: ...`; a driver that hangs is killed after 22s.

- Clicking Open through AT-SPI does not confirm a path typed into the entry, so it is not used.
- GTK's location entry autocompletes, and the first activation may only accept the completion. So the entry is activated until the dialog closes, at most 3 times, and before each activation its text must still be the requested path: a completion that changed it would open a different file, so that fails instead.
- `xdotool` was considered and rejected as fragile: it depends on window focus, sends synthetic keystrokes that land wherever focus is, and depends on keyboard layout and language.

### Shelf, language and persistence

- Shelf tasks and checks (`screenplay/shelf/`): `RemoveFromShelf(title)`, `SeeShelfLacks(title)`, `SwitchShelfLanguage`, `SeeShelfLanguage`, `ToggleShelfTheme`, `SeePlayerTheme`, `SeeRunLinkText(title, text)` (a card's run link text), `CurrentPlayerTheme()` (a one-shot read of the body's theme: settle startup first). `SeeShelfLacks` is an absence check, so it needs a settled anchor first (a positive shelf state). The pause screen's language is switched with `SwitchPauseLanguage` and read with `SeePauseLanguage`, and its Preferences heading with `SeePreferencesLabel` (`screenplay/pause/`).
- `SeeShelfWritesSettled()` waits for `data-pending-writes` on the shelf to be `0`. The shelf changes optimistically, so its cards say nothing about storage: call it before `RestartPlayer()` and after a check that proves the triggering change re-rendered (otherwise the counter may still be 0 before the change started).
- `support/translations.ts` (`translation(lng, key)`, `pluralTranslation(lng, key, count)`) reads the expected text from the player's locale files, so a scenario states the language and not the wording. It runs in Node, not in the page. It reads only the `translation` namespace (the player's i18n default namespace is `theme`, falling back to `translation`), so a string a `theme`-namespace file overrides would be missed. A key missing from a language falls back to `en`, as i18next's `fallbackLng` does.

### Single-target scenarios

`scenario(title, body)` runs on both targets; each target's shim (`targets/<target>/scenario.ts`) maps it to its runner. When a step exists on only one target, split the scenario into `scenario.webOnly(...)` and `scenario.desktopOnly(...)` variants with the **same base title**. On the other target a variant shows as skipped, never silently absent. Titles get a ` (web only)` / ` (desktop only)` suffix, because Playwright rejects duplicate titles. **Never branch inside a scenario.**

### Failure locations

Failure messages carry the scenario file and line as a `[scenarios/x.scenario.ts:N]` prefix. Playwright's list reporter still names the shim file as the test location (the prefix and a `scenario` annotation carry the real one). The WDIO spec reporter prints `(root)` without titles; Serenity's console reporter carries the detail, so read that.

### Themes

Elements use only the theme contract, so they are the same under every theme. The machinery:

- `forEachTheme(variants, title, body, { webOnly })` (`screenplay/support/for-each-theme.ts`) registers one scenario per variant, titled `title [variant name]`. The variants are `CORE_THEME_VARIANTS` in `fixtures/themes-game.ts` (`aero` and `custom`); each carries the theme alias and the zip of the e2e game packed with that theme selected (`mode = "aero"`, or `themes` plus `defaultTheme`). `core-flow-themes.scenario.ts` runs the core flows (actions update the text, load restores a save) through it.
- `SeeActiveTheme(alias)` (`common/checks.ts`) reads the `data-qsp-theme` marker the renderer puts on `qsp-game-root` (`THEME_ALIAS`: `qspider:classic`, `qspider:aero`, `e2e-custom`).
- UI a theme renders outside the `qsp-*` vocabulary gets elements under `screenplay/themes/<theme>/` (`e2e-custom` exists: the theme's chrome and script marker).
- The classic layout's docks carry `data-qsp-dock` (`top`, `left`, `center`, `right`, `bottom`); their elements and checks are `screenplay/classic/` (`SeeStatsInDock`).
- `themes.scenario.ts` covers theme features: Aero mode, a game-provided theme with its files, the missing-`defaultTheme` fallback and notice, runtime `change_theme` (and its unknown-name error), a theme-level layer cleared by restart, and the `qspgui.cfg` docks against a control without it. The css-link check reads a custom property the theme's css sets on its chrome.
- The look variables (Aero and classic) are theme features too, so they also run once per target:
  - `look-vars.scenario.ts`: the Aero and classic mapping tables, that the variables reach the dialog portal, `qspgui.cfg` colours and font (and that the game beats the cfg), a cfg-less game's default look, Aero `$*_FORMAT` wrappers and that they do not leak.
  - `look-dialogs.scenario.ts`: `DISABLESHADE`, the `MSG` / `INPUT` / `MENU` positions, `FIXED_SIZE_MENU`, `ALWAYS_SHOW_VIEW`.
  - `look-effects.scenario.ts`: a slow fade is in flight; a quick slide and a sequential fade (one scenario) still deliver the new location.
  - The mapping tables must cover every variable the themes read: `build-fixtures.spec.ts` parses `aero.html` and `classic.html` and fails when a variable has no table row.
  - Fixtures: `look-game` (an Aero and a classic zip; markers only through `fixtures/look-game.ts`) and `gui-cfg-game` (the cfg colours, plus a 'Set look' action).
  - Values are read with `SeeCssValues`; the probe rules are in the support section above.

The matrix: the core flows run under aero and custom on web only (`webOnly`; they show as skipped on desktop). Desktop runs each theme-feature scenario once, in `themes.scenario.ts` and the `look-*.scenario.ts` files. The desktop-specific risk is theme files loaded through the Tauri protocol and Aero under WebKit, not the markup contract, which is the same code on both targets. Rationale: `docs/superpowers/specs/2026-10-20-e2e-conventions-design.md`.

Extra arguments to that script go to `wdio run`.
- `pnpm nx test player-e2e` - unit tests for the harness itself: the desktop prerequisite check (`targets/desktop/check-prereqs.ts`), and the private-session guard (`targets/desktop/private-session.ts`).
- `pnpm check` runs those unit tests, then `e2e:web` and `e2e:standalone-web` as its last steps; `pnpm check:full` adds `e2e:desktop` and `e2e:standalone-desktop`.
- `pnpm e2e:standalone-web` - `nx run player-e2e:e2e-standalone-web` (stage, build, serve, Playwright; see "Standalone").
- `pnpm smoke:desktop` - the desktop launch smoke of both desktop apps, no WebDriver (see "Launch smoke"). Not part of `pnpm check` or `pnpm check:full`; CI runs it on macOS.
- `pnpm e2e:standalone-desktop` - the desktop prerequisite check, then `nx run player-e2e:e2e-standalone-desktop`. It passes no extra arguments to wdio. To run part of the suite, build once with `pnpm nx run player-e2e:build-desktop-standalone-e2e`, then `node apps/player-e2e/targets/desktop/run-desktop-e2e.mjs --standalone --spec …`. That uses the standalone binary as last built: rebuild after any change outside `apps/player-e2e`.

## Standalone

The standalone player (`apps/player-standalone`) has its own small suite, `scenarios/standalone/`, on both targets. The main web and desktop configs skip it (`testIgnore: standalone/**`, wdio `exclude`), and it has its own targets in `project.json`:

- `stage-standalone` (`targets/standalone/stage-public.ts`): copies `public/` without `game/` to `dist/e2e/standalone-public/` and adds the fixture game (`fixtures/standalone/`). The build takes it as `publicDir` through `QSPIDER_E2E_STANDALONE_PUBLIC_DIR` (`apps/player-standalone/vite.config.mts`). The repo's `public/game/` is never read or written by the E2E; do not point anything at it. The standalone build always empties its `outDir`.
- `build-standalone-web-e2e` and `e2e-standalone-web`: build with `--skip-nx-cache` (a cached build would hide a stale game), check that the built `game.cfg` is byte-identical to the fixture (`targets/standalone/check-build.ts`), then run Playwright with `targets/web/playwright.standalone.config.ts`. It serves `dist/apps/player-standalone` with `vite preview` on port 4310 (deliberately not `nx preview`).
- `build-desktop-standalone-e2e` and `e2e-standalone-desktop`: `tools/standalone-config` turns `fixtures/standalone/qspider.desktop.json` into the Tauri overlay `dist/e2e/tauri.standalone-e2e.json`, then `pnpm tauri build --debug --no-bundle -c <overlay>` builds with `CARGO_TARGET_DIR=target/e2e-standalone` (relative to `src-tauri`, where Tauri runs cargo), giving `src-tauri/target/e2e-standalone/debug/qspider`, and the same `check-build.ts` runs. The suite then runs through `run-desktop-e2e.mjs --standalone` (the flag may stand anywhere in the arguments; it is not passed on to wdio), which picks `wdio.standalone.conf.ts` (`wdio.conf.ts` is a `desktopConfig()` factory). The artifacts, a11y log included, go to `artifacts/desktop-standalone/`.
- There is no shelf, so the scenarios wait for the startup marker (`[data-qa="startup-finished"]`, `StartupMarker` from `libs/renderer`) instead of a shelf. A desktop standalone app can quit (the game's quit action closes the window): `ClickActionClosingTheApp(label)` clicks such an action and accepts the session ending under it, and `SeeAppClosed()` then checks, through `appRunning`, that no app process remains. The fresh-app step tolerates an app that exited during the previous scenario (it logs a warning).

## Prerequisites

Web:

- Chromium. Either `CHROME_BIN=/usr/bin/chromium` (use a system browser) or `pnpm exec playwright install chromium`. With neither, Playwright fails with its install message.

Desktop:

- Rust toolchain.
- `tauri-driver`: `cargo install tauri-driver --locked`, with `~/.cargo/bin` on `PATH`.
- `WebKitWebDriver`: Arch `webkit2gtk-4.1`; Debian/Ubuntu `webkit2gtk-driver` (`webkitgtk-webdriver` on Ubuntu 26.04+).
- Linux (the run is always headless, see "Desktop runs on Linux"): `xvfb-run`, `dbus-run-session`, `dbus-send`, the AT-SPI daemons (`at-spi-bus-launcher`, `at-spi2-registryd` in `/usr/libexec` or `/usr/lib`) and `python3` with `gi.repository.Atspi`. Arch: `xorg-server-xvfb dbus at-spi2-core python-gobject`; Debian/Ubuntu: `xvfb dbus at-spi2-core python3-gi gir1.2-atspi-2.0`. No display is needed.
- Port 4444 free (tauri-driver's port).

A missing tool, AT-SPI daemon or AT-SPI Python bindings, or a busy port 4444 makes `pnpm e2e:desktop` fail with a message naming it. Web E2E likewise fails if port 4300 is already in use; it never reuses a running server.

## Desktop runs on Linux

`targets/desktop/run-desktop-e2e.mjs` runs, from the workspace root, roughly the equivalent of the following (a sketch, not a recipe: the script also pins `node`/`python3`, strips more of the session's env, manages the process group and removes the private dir):

```bash
d="$(mktemp -d)" && mkdir "$d"/config "$d"/data "$d"/cache "$d"/state && \
env -u WAYLAND_DISPLAY -u AT_SPI_BUS_ADDRESS -u DBUS_SESSION_BUS_ADDRESS -u XDG_SESSION_TYPE \
  -u XDG_CURRENT_DESKTOP -u XDG_SESSION_DESKTOP -u PULSE_SERVER -u PIPEWIRE_REMOTE -u GTK_MODULES \
  -u SSH_AUTH_SOCK -u HYPRLAND_INSTANCE_SIGNATURE -u GDK_SCALE -u GDK_DPI_SCALE -u QT_SCALE_FACTOR \
  -u QT_AUTO_SCREEN_SCALE_FACTOR -u GTK_THEME -u XCURSOR_SIZE \
  XDG_RUNTIME_DIR="$d" XDG_CONFIG_HOME="$d/config" XDG_DATA_HOME="$d/data" \
  XDG_CACHE_HOME="$d/cache" XDG_STATE_HOME="$d/state" GSETTINGS_BACKEND=memory \
  GDK_BACKEND=x11 GIO_USE_VFS=local GVFS_DISABLE_FUSE=1 QSPIDER_E2E_PRIVATE_SESSION=1 \
  xvfb-run -a -s '-screen 0 1280x1024x24' dbus-run-session -- apps/player-e2e/targets/desktop/atspi/with-a11y-bus.sh \
  wdio run apps/player-e2e/targets/desktop/wdio.conf.ts [args]
```

Nothing in the run may touch your desktop session or your home, so the layers nest outside-in:

- `xvfb-run -a -s '-screen 0 1280x1024x24'` is the outermost layer: everything inside sees only its virtual `DISPLAY`, on a screen of a fixed size (the xvfb-run default varies by distribution, 640x480 on Arch, and is too small for the app; pinning it gives every machine and CI the same size). `WAYLAND_DISPLAY` is removed and `GDK_BACKEND=x11` set, so GTK uses Xvfb even on a Wayland desktop: no window appears on your screen.
- A fresh private dir (0700, removed when the run ends) covers the whole tree: the private bus, the services it activates (dconf, portals), wdio and the app. It is `XDG_RUNTIME_DIR`, and `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME` and `XDG_STATE_HOME` point at subdirectories of it. `GSETTINGS_BACKEND=memory` keeps settings out of dconf. So nothing writes `~/.config/dconf/user`, `~/.local/share/recently-used.xbel` or the like. `wdio.conf.ts` still sets its own per-run `XDG_DATA_HOME`/`XDG_CONFIG_HOME`/`XDG_CACHE_HOME` for tauri-driver and the app, which take precedence. Every variable that points at the desktop session is removed: `AT_SPI_BUS_ADDRESS`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_SESSION_TYPE`, `XDG_CURRENT_DESKTOP`, `XDG_SESSION_DESKTOP`, `PULSE_SERVER`, `PIPEWIRE_REMOTE`, `GTK_MODULES`, `SSH_AUTH_SOCK` and `HYPRLAND_INSTANCE_SIGNATURE` (and `WAYLAND_DISPLAY`, above). The host's display scaling and look are removed too: `GDK_SCALE`, `GDK_DPI_SCALE`, `QT_SCALE_FACTOR`, `QT_AUTO_SCREEN_SCALE_FACTOR`, `GTK_THEME` and `XCURSOR_SIZE`. A leaked `GDK_SCALE=2` would make the screen count as half its size in logical pixels and collapse the app's layout. Version-manager shims would read their state from the replaced XDG dirs, so `node` and `python3` are pinned (symlinked in the private dir) to the interpreters resolved with the real env. `GIO_USE_VFS=local` and `GVFS_DISABLE_FUSE=1` keep gvfs from mounting anything.
- `dbus-run-session` gives the run a private session bus.
- `atspi/with-a11y-bus.sh` starts the AT-SPI accessibility bus and registry on that bus. A bare `dbus-run-session` can't activate them (D-Bus would ask systemd), so the script starts `at-spi-bus-launcher --launch-immediately` and `at-spi2-registryd` itself, from `/usr/libexec` on Debian/Ubuntu or `/usr/lib` on Arch, and exits 1 naming a missing one. It fails closed: it refuses to run (exit 1) without `QSPIDER_E2E_PRIVATE_SESSION=1`, when `DBUS_SESSION_BUS_ADDRESS` is unset or is the desktop bus (`/run/user/$UID/bus`), or when `org.a11y.Bus` already has an owner. The daemons run without `DISPLAY`, so they can't publish `AT_SPI_BUS` on any X server, and with their own runtime dir. The script polls until the bus and then the registry answer, runs the command, then stops the two daemons it started (TERM, then KILL after about 2s) and exits with the command's status. The daemons' output goes to `artifacts/desktop/a11y-bus.log`, which is copied before any KILL. The AT-SPI bus lets tests drive native GTK dialogs (the file picker) from Python.
- The runner starts the tree in its own process group. On Ctrl-C (or TERM/HUP) it passes the signal to the whole group and exits with `128+n`. When the child exits, normally or not, it TERMs what is left of the group (for example, services the private bus activated), waits up to 30s, then KILLs, and only then removes the private dir.

Trade-off: the tree is a separate process group, so the terminal's Ctrl-C reaches it only through the runner. If the runner itself is SIGKILLed (or crashes), nothing forwards signals or cleans up: Xvfb, the private buses, wdio, tauri-driver and the app can be orphaned, and the private dir under `$TMPDIR` (`qspider-e2e-runtime-*`) stays behind. Find them by that process group (`ps -o pid,pgid,cmd`) and kill that group, not processes by name.

On Windows and macOS the script runs `wdio run …` directly. CI runs plain `pnpm e2e:desktop`.

Don't rebuild that environment by hand. To run part of the suite, pass wdio arguments through the runner: `pnpm e2e:desktop --spec apps/player-e2e/scenarios/core-flow.scenario.ts`, or, with the E2E binary already built, `node apps/player-e2e/targets/desktop/run-desktop-e2e.mjs --spec …`. To inspect the dialog's accessibility tree, temporarily call `dialog.py dump` from a scenario run this way; `dialog.py` refuses to run outside the runner's session.

## Launch smoke

A launch check of both desktop apps without WebDriver, so it runs where `tauri-driver` does not (macOS). `pnpm smoke:desktop` runs (both always, failing if either failed; CI runs them as two separate steps) `nx run player-e2e:smoke-desktop` (the main desktop player, launched with `fixtures/e2e-game/e2e-game.qsps`, expecting `E2E START`), then `nx run player-e2e:smoke-desktop-standalone` (the desktop standalone player, expecting `STANDALONE START`). Each builds its E2E debug binary first (`build-desktop-e2e`, `build-desktop-standalone-e2e`, as above). The expected texts are literal in `project.json`; `fixtures/e2e-game.ts` and `fixtures/standalone-game.ts` are the source of truth, so keep them in step.

- The channel: in an E2E build (`VITE_QSPIDER_E2E=true`), `libs/desktop/src/lib/e2e-marks.ts` reports, once each and in this order, `startup-finished`, `game-running <game id>` and `main-text <text>` (the first non-empty main description as plain text: `textContent` of the parsed HTML, so newline characters become spaces but `<br>` and block boundaries add nothing, e.g. `<p>A</p><p>B</p>` gives `AB`; fixture start texts must stay single-block). It calls the `e2e_mark` command (`src-tauri/src/e2e.rs`), which prints `QSPIDER_E2E_MARK <marker>[ <detail>]` on stdout. The command exists only under `debug_assertions`, and the reporter runs only in an E2E build, so release builds carry neither.
- The runner, `targets/smoke/run-smoke.mjs --app <binary> [--file <game>] --expect-text <text> [--timeout-ms N] [--alive-ms M] [--host-session]` (defaults: 60000 and 5000), launches the binary and reads its stdout. It passes when the three markers arrive in order within N ms, `main-text` (trimmed) equals `--expect-text` exactly, and the app is still running M ms after the last marker. A repeated marker is ignored; a marker ahead of the one awaited fails the run, and so does an app exit before or during that window. On failure it prints the reason, every marker received and the last 50 output lines. It then stops the app (TERM, then KILL after 5s).
- Linux: the runner uses the desktop E2E's private session (`targets/desktop/private-env.mjs`, see "Desktop runs on Linux", without the AT-SPI bus). Started outside it, it re-runs itself under Xvfb and a private D-Bus with private XDG dirs; started with `QSPIDER_E2E_PRIVATE_SESSION=1` it refuses unless the session really is private. The app stays in the session's process group: the runner stops it by PID, and the outer runner then stops the whole group.
- macOS (and Windows): there is no private session. The app runs with the host env and writes the user's real app data (`~/Library/Application Support/…` on macOS), so the runner refuses unless `CI` is set (GitHub Actions sets `CI=true`; a CI machine is throwaway). On a developer Mac, run it directly with `--host-session` only if that is intended: `node apps/player-e2e/targets/smoke/run-smoke.mjs --app src-tauri/target/debug/qspider --file apps/player-e2e/fixtures/e2e-game/e2e-game.qsps --expect-text 'E2E START' --host-session` after `pnpm nx run player-e2e:build-desktop-e2e`. On macOS the app gets its own process group and is stopped as a group.
- The markers come from game state (`startupFinished$`, `currentGameEntry$`, `mainContent$`): the app reports the start text, it does not prove it was rendered. A render failure with correct state is covered by the Linux WebDriver suites only.
- What it tells apart (checked on Linux by breaking it on purpose): a wrong start text (`main-text was "…", expected "…"`), markers out of order (`markers out of order: got main-text while waiting for startup-finished`), an app that exits right after its first screen (`app exited (code 0) during the liveness window`) and an app that never gets there (`timeout waiting for startup-finished`). It does not check anything after the first screen; that is the WebDriver suites' job.

## CI and branch protection

Workflows: `.github/workflows/checks.yml` (every PR), `.github/workflows/desktop-build.yml` (build-only on Windows and macOS; path-filtered), `.github/workflows/smoke-macos.yml` (the macOS launch smoke, a reusable workflow called by `checks.yml` and `scheduled-desktop-build.yml`) and `.github/workflows/scheduled-desktop-build.yml` (weekly). Branch protection, by the names GitHub shows in the checks list:

- Required checks on `main` (ruleset "main"): `frame`, `rust`, `e2e-web`, `e2e-desktop`, `e2e-standalone-web`, `e2e-standalone-desktop`, `smoke-macos / smoke`.
- `rust` (fmt, clippy, cargo test) runs on a PR only when `src-tauri/`, `checks.yml` or `package.json` changed. The `changes` job decides, and a job skipped by its `if:` counts as passing. On `main` it always runs. Rust compile errors are still caught on every PR, because `e2e-desktop` and `e2e-standalone-desktop` build the Tauri app.
- The Tauri build dependencies are restored from an apt cache shared by `rust`, `e2e-desktop` and `e2e-standalone-desktop`. To invalidate it, bump `APT_CACHE_VERSION` in `checks.yml`. The packages that need post-install setup (WebDriver, Xvfb, dbus, AT-SPI) are installed with plain apt, with a timeout and retries.
- `smoke-macos / smoke` (the name GitHub shows for the `smoke` job of `smoke-macos.yml` called by the `smoke-macos` job): the two smokes (`smoke-desktop`, `smoke-desktop-standalone`) as separate steps on `macos-latest`, so a failure of one never hides the other. On a PR it runs only when desktop-relevant files changed, and is skipped otherwise; a skip counts as passing. The relevant files are the desktop code (`src-tauri/`, `libs/desktop/`, `libs/tauri-storage/`, `apps/player-desktop/`, `apps/player-standalone/`), the smoke and what it depends on (`apps/player-e2e/targets/smoke/`, `apps/player-e2e/project.json`, `apps/player-e2e/fixtures/e2e-game/`, `fixtures/standalone/`, `fixtures/e2e-game.ts`, `fixtures/standalone-game.ts`, `targets/desktop/private-env.mjs`, `targets/desktop/private-session.ts`, `targets/standalone/`, `tools/standalone-config/`), `package.json`, `pnpm-lock.yaml`, `smoke-macos.yml` and `checks.yml`. The `changes` job's `desktop` output decides. The gate is the reusable workflow's `run` input, not an `if:` on the caller: a caller job skipped by `if:` would show only as `smoke-macos` (skipped), and a required `smoke-macos / smoke` would then wait forever. With the input, the check is expected to be named `smoke-macos / smoke` whether it runs or is skipped. That is GitHub's documented behaviour; confirm it on the first PR where the smoke is skipped. It always runs on `main`, and weekly from `scheduled-desktop-build.yml`, where a failure opens or updates the same tracking issue as the build. It can also be started by hand (`workflow_dispatch`). The shared frontend libraries (e.g. `libs/renderer`, `libs/game-state`) are not in the path list: a PR changing only those is smoke-tested on macOS only after it lands on `main`.
- Not required: `build-desktop (…)` (the `desktop-build.yml` matrix jobs). The workflow is path-filtered, so a required check would block PRs where it never runs.
