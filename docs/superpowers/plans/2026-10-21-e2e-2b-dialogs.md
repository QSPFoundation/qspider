# Batch 2b — Dialogs & blocking calls E2E Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cover the engine's blocking overlays end-to-end — `msg`, `input`, `menu`, `view`, `wait` — plus Esc-while-open and hotkey-during-dialog behaviour, on both web and desktop, proving each resolves back to the engine correctly.

**Architecture:** One new fixture game (zip: `game.cfg` + `dialogs.qsps` + a view image) whose start location has an action per dialog, opened via the existing `OpenGameFile`. Five new screenplay areas (`msg/`, `input/`, `menu/`, `view/`, `wait/`), each `elements.ts`/`tasks.ts`/`checks.ts`, located only by `data-qsp` markers (all present today except two small markers this batch adds). Scenarios in `scenarios/dialogs.scenario.ts` and a cross-cutting `scenarios/blocking-calls.scenario.ts`. Results are observed through the engine's response: dismissing/selecting changes `game/MainText`.

**Tech Stack:** Serenity/JS screenplay; Playwright (web) + WebdriverIO/tauri-driver/AT-SPI (desktop); Vitest via NX; the batch-2a fixture builder (`fixtures/build-fixtures.ts`) and `OpenGameFile` ability.

**Spec:** `docs/superpowers/specs/2026-10-21-e2e-phase2-design.md` (batch 2b) + companion inventory `docs/superpowers/specs/2026-10-21-e2e-engine-inventory.md` (§C).

## Global Constraints

- Run all tasks through NX targets (`nx run player-e2e:e2e-web` / `:e2e-desktop`, `nx run <proj>:test`), never direct playwright/wdio/vitest. Web E2E needs `CHROME_BIN=/usr/bin/chromium`; desktop E2E runs only via `pnpm e2e:desktop` with `PATH="$HOME/.cargo/bin:$PATH"` (never `wdio` or the a11y wrapper directly; never touch the real desktop session).
- Follow `apps/player-e2e/README.md`: area = screen/overlay, one noun; `elements.ts`/`tasks.ts`/`checks.ts` split; locate ONLY by `[data-qsp*]` / `[role=]` / `[data-qa]` (never text/class/nesting); checks via `seeEventually`, never `Ensure`; `tasks.ts` imports checks only from `common/checks.ts`; **no fixed sleeps** (`Wait.for` fails lint); no dynamic `import()` outside `support/scenario.ts`; `screenplay/**` files ≤150 lines; `await` every `attemptsTo`.
- Scenarios run on BOTH targets (plain `scenario(...)`) unless a behaviour is target-specific. 2b uses the DEFAULT (classic) theme only — aero dialog variants are deferred to batch 2f (`forEachTheme`). Do not add theme handling here.
- Fixture descriptor modules (`fixtures/*.ts`) stay free of any test-framework import.
- `pnpm check` must stay green; all required checks (`frame`, `rust`, `e2e-web`, `e2e-desktop`) pass before merge. One PR for the batch.
- Two additive `data-qsp` test markers are introduced (wait-lock, menu separator). They are not behaviour changes. If the hotkey-during-menu scenario (Task 7) exposes a real crash, fixing it is an in-batch ⚠ change — flag it in the PR body.
- NOT in 2b: the SETTIMER counter and counter-pause-during-dialog (→ batch 2e); aero/`ALWAYS_SHOW_VIEW`/theme-specific dialog layout (→ batch 2f).

## Review Focus

- **Esc while a dialog is open:** Radix also closes the dialog on Esc. The assertion is that the pause screen (`[data-qsp="pause-screen"]`) does NOT appear — it must tolerate the dialog itself closing. Pinned in Task 7.
- **menu cancel vs select:** selecting item N returns its index (engine jumps to that location); cancelling returns -1 (a different location/result). Both paths exercised. Pinned in Task 4.
- **input cancel returns '' vs submit returns the typed text:** both must be observed via the engine echoing the result into main text. Pinned in Task 3.
- **hotkey during menu is unguarded** (menu does not set `isPaused$`, unlike msg/input/wait): pressing an action hotkey while a menu is open runs the underlying action — the most likely re-entrancy/crash path. Treat a crash as a product finding and fix in-batch (⚠). Pinned in Task 7.
- **view image is async:** assert the `[data-qsp="view-image"]` element is present, not that the bitmap painted; the image must be bundled in the fixture zip. Pinned in Tasks 1 and 5.
