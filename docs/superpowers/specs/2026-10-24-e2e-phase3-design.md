# E2E Phase 3: More Platforms (Design)

Date: 2026-10-24
Status: draft, pending maintainer approval
Parent: `2026-10-20-automated-checks-design.md` ("Phase 3"). This document widens that section with the standalone builds (the former 2i) and sets the order.

## Intent

This is the same goal as every phase: enough automated coverage that the maintainer (and agents) can change code without fear of breaking it. Phases 1–2 cover the web player (Chromium) and the Linux desktop player (WebKitGTK) feature by feature. Three shipped surfaces are still unchecked:

- the standalone player that game authors bundle their game with (web and desktop);
- the Windows desktop app (WebView2 / Chromium, Windows paths and file system, Windows file dialog);
- the macOS desktop app (WKWebView, macOS platform layer).

Today the cross-OS desktop apps are only _built_ (`desktop-build.yml` on `src-tauri/**` PRs; `scheduled-desktop-build.yml` weekly). Nothing launches them.

## Order and shape

Three PRs, in this order. Each is green on its own and follows the Phase 2 conventions (`apps/player-e2e/README.md` rules; the scenario quality bar; ⚠ defects fixed in the same PR, red then fix, asking the maintainer first only for player-visible changes).

1. **Standalone** (web + desktop-standalone). It runs on the maintainer's Linux machine with the existing harness, so the feedback loop is fast.
2. **macOS launch smoke**. Small, CI-only.
3. **Windows desktop E2E**, the full suite. The largest and riskiest PR; CI-only.

## Goals

- Standalone: the bundled game starts by itself and the standalone-specific paths work, on web and on desktop-standalone built the way a game author builds it.
- macOS: the desktop app (main player and standalone) launches, loads a real game and shows its first location, with no crash.
- Windows: the whole desktop scenario suite passes on `windows-latest`.

## Non-goals

- Re-running the full player suite against standalone. Standalone shares the libraries the player suite already covers; only standalone-specific behaviour is tested.
- Full E2E on macOS (no WebDriver for WKWebView via tauri-driver).
- Testing the native file dialog's own UI (it is driven, not tested; same as Linux).
- Testing `tools/standalone-config` through its API (memory "no tests for tool config"); it is exercised by running the real CLI on a real input.
- Release/bundle artifacts (installers, `.dmg`, signing).

## Anti-goals

- Coverage that tests a configuration no real game ships with. That's why standalone desktop is built through the author pipeline.
- Windows "passing" through `windowsOnly` skips or relaxed checks. A scenario that can't pass on Windows because of a player defect is a defect (fix or ask), not a skip. A genuine harness limit (like `sendKeys` on WebKit) is a target-specific variant with a stated reason, reviewed like the WebKit ones.
- Test hooks in release builds. Everything test-only stays behind the existing E2E build switch (`VITE_QSPIDER_E2E=true` + debug build) or an equivalent compile-time gate.
- Flakes absorbed silently. Retries only where a known, documented cause exists (as with #167).

## Constraints

- The maintainer develops on Linux (Arch, Wayland). There's no Windows or macOS machine: **GitHub Actions is the only way to run Windows and macOS.** Every Windows/macOS iteration is a CI round.
- The repo is public: macOS/Windows runner minutes are free, with org-level concurrency limits (macOS: 5).
- The desktop E2E build today is `pnpm tauri build --debug --no-bundle` with `VITE_QSPIDER_E2E=true` (`player-e2e:build-desktop-e2e`). Rust has no e2e cargo feature.
- `targets/desktop/fresh-app.ts` (per-scenario isolation) relies on XDG dirs and `/proc`: Linux-only.
- The native-dialog driver (`targets/desktop/atspi/dialog.py`) is Linux-only (AT-SPI). The README already promises Windows uses UI Automation "behind the same `openGameFile`: no scenario changes".
- Never touch the maintainer's real desktop session (memory "never-touch-real-session"). This applies to any local run of the standalone desktop target.
- Branch protection ("main" ruleset) is maintainer-owned. Changing its required checks is an outward action: ask before doing it.

## PR 1: Standalone

### What exists

- `apps/player-standalone/src/app/init.ts` fetches `game/game.cfg` relative to `index.html`, runs `runConfig` (plain base URL) on it, starts the **first** `[[game]]` with `runGame`, then sets `baseInit$`. There is no shelf, no `initTheme` (so no player theme or `player-body` marker), and no service worker. `onGameEnd$` closes the window (engine `QUIT`). `checkForUpdates()` runs at startup.
- Web build: `nx build player-standalone`. Desktop build: `player-standalone:build:desktop`, used by Tauri via an overlay on `src-tauri/tauri.conf.json` (`standalone.conf.json` in this repo; for game authors, the overlay generated by `tools/standalone-config` from `qspider.desktop.json`).
- The **generated** overlay sets `productName`, `identifier` (so a **different app-data directory**), the window title and size, and removes the `updater` plugin config unless the author enabled it (the Rust `setup` then skips the updater plugin). The in-repo `src-tauri/standalone.conf.json` sets only `build.*`. The base config already has `visible: false` and `useHttpsScheme: true`, so those are shared with the main desktop app.
- The generated overlay's `beforeBuildCommand` is `pnpm run build:standalone-desktop`, so `tauri build -c <overlay>` rebuilds the frontend (Vite empties `outDir`) and embeds `frontendDist` in the binary. Files copied into `dist/` before the Tauri build are wiped.
- `qspider-standalone-game-template` (v1-era workflows) checks the game repo out into **`public/game/`** of a qspider checkout, then builds; `public/game/*` is gitignored except `.gitkeep`. `publicDir` (`../../public`) is shared by `player`, `player-desktop` and `player-standalone`.

### What is tested (maintainer-approved depth)

On **web-standalone** and **desktop-standalone**:

1. The bundled game starts by itself (no shelf, no Open game step).
2. It's playable: an action runs and the main description updates.
3. Save and load work (the standalone app's own storage; on desktop, under the author's `identifier`).
4. `game.cfg` resources and the game's theme apply.
5. Desktop only: an engine `QUIT` closes the window.

### How the targets are built

- **Desktop-standalone goes through the real author pipeline** (maintainer decision): a fixture `qspider.desktop.json` → `pnpm standalone:config <it> --out <overlay>` → the E2E debug build (`tauri build --debug --no-bundle -c <overlay>`, `VITE_QSPIDER_E2E=true`), with the fixture game copied into the standalone `game/` folder. The game reaches `frontendDist` through a public dir's `game/` folder, as in the template, but **never the repo's own `public/game/`** (maintainer decision: the maintainer sometimes keeps a local test game there). E2E builds stage a copy of `public/` in a temporary/artifacts dir, put the fixture game in its `game/`, and point the standalone build at it through an E2E-only env var read by `apps/player-standalone/vite.config.mts` (`publicDir`). Unset, the build behaves exactly as today, so neither players nor the template see a change. The main `player` / `player-desktop` builds are unaffected.
- **Web-standalone**: `player-standalone:build` with the fixture game in `game/`, served as plain static files.
- Both are new NX targets in `player-e2e`, next to the existing ones.

### Harness

- A new standalone target per platform under `apps/player-e2e/targets/standalone/` (or `targets/web` / `targets/desktop` configs, whichever reuses more). Scenarios go in a new `standalone` screenplay area, run only by the standalone targets; the existing suite is untouched. Builder's call: whether standalone scenarios are a separate scenario directory or are selected by name/tag.
- **Startup marker (Claude's call):** standalone gets its own invisible marker equivalent to `data-qa="startup-finished"`, set once `init()` has finished (after `runGame`), so `SeeStartupFinished()` works and nothing sleeps. It's a hidden data attribute, so it isn't player-visible.
- Desktop-standalone isolation on Linux works as today: each run gets its own `XDG_*` dirs and `fresh-app.ts` empties them, whatever the identifier. The tauri-driver launch carries no game argument (standalone ignores it).
- **One binary path for both builds:** the main E2E build and desktop-standalone both produce `src-tauri/target/debug/qspider(.exe)` (hard-coded in `wdio.conf.ts`), and the Tauri config is compiled in, so each build overwrites the other and forces a Rust recompile. The builder keeps them apart (separate `CARGO_TARGET_DIR`, or copying each binary to its own path) and makes `check:full` ordering safe.
- **Fixture game (Claude's call):** a small new standalone game in `apps/player-e2e/fixtures/standalone/` (`.qsps` + TOML `game.cfg`), built by `build-fixtures.ts`, reusing the existing resource/theme fixture assets where possible. Markers are ALL-CAPS constants in a `fixtures/standalone-game.ts`. ≤ 8 actions per location. The `game.cfg` lists **two** games, so the scenario proves the first one is the one that starts.
- `checkForUpdates()` is already gated in E2E builds (`libs/desktop/src/lib/updater.ts`); the fixture `qspider.desktop.json` leaves the updater disabled anyway.

### Local and CI

- `pnpm check` gains web-standalone; `pnpm check:full` gains desktop-standalone. Builder's call: whether they fold into `e2e:web` / `e2e:desktop` or are separate scripts that those call.
- CI: **separate jobs next to** `e2e-web` and `e2e-desktop` (they run in parallel, so they don't add wall time). Names: `e2e-standalone-web`, `e2e-standalone-desktop`. They're required once green; Claude asks the maintainer before changing the ruleset.

## PR 2: macOS launch smoke

### What it checks (maintainer decision: load a real game)

On `macos-latest`, for **two builds**: the main desktop player (E2E build) and desktop-standalone (built through the same author pipeline as PR 1):

1. The app launches. For the main player, a fixture game is passed on the command line (`filePath` / `-f`, the Tauri CLI plugin route that already exists); standalone uses its bundled game.
2. The app reports, in order: **startup finished**, **game running**, and **the first location's text**.
3. Pass = all three arrive within N seconds (builder picks N with a margin over observed CI times) and the process is still alive. Fail = timeout or crash, with the app's stdout/stderr and the received markers in the job log.

### How the app reports (no WebDriver)

- An E2E-build-only channel from the frontend to the test process: the frontend emits the three markers (derived from the same state the E2E markers use: `startupFinished$`, the running game, the main description), and they reach the test process (for example a Tauri command that prints a prefixed line to stdout, or a file under a path given by an env var). Builder's call, within these limits:
  - absent from release builds (compile-time gated: Vite `VITE_QSPIDER_E2E` on the frontend, and `debug_assertions` or a cargo feature on the Rust side if Rust is involved);
  - no new production dependency;
  - the same channel works on Linux, so the smoke runner can be developed and run locally on the maintainer's machine before CI (in the private session, never the real one).
- The smoke runner is a small Node script in `apps/player-e2e/targets/smoke/` (or similar), with an NX target.

### Trigger (maintainer decision)

- On PRs: only when desktop-relevant paths change: `src-tauri/**`, `libs/desktop/**`, `libs/tauri-storage/**`, `package.json`, `pnpm-lock.yaml`, the workflow file. Builder may extend the list with a stated reason (for example `apps/player-desktop/**`, `apps/player-standalone/**`).
- Always on push to `main` and in the weekly scheduled build.
- Required check; a skipped run counts as passing (same pattern as `rust`, using the `changes` job).
- Reasoning on record: WebKit-family frontend regressions are already caught by the Linux desktop suite (WebKitGTK); macOS-specific risk is mostly the platform layer, dependency bumps and Safari-version lag.

## PR 3: Windows desktop E2E

### Scope (maintainer decision: full suite)

All desktop scenarios run on `windows-latest` (tauri-driver + msedgedriver, WebView2). The standalone desktop scenarios from PR 1 also run there.

**Trigger (maintainer decision): every PR, required**, plus `main`. Unlike macOS, Windows is the only place that combines Chromium with Tauri (the `tauri.localhost` origin, storage, resource URLs), and those live in frontend libs a path filter would skip. To keep wall time near the Linux desktop job, the builder may shard the suite across parallel Windows jobs (one required check per shard, or one aggregating job), with a timeout fitted to measured CI times.

### What needs building

1. **Driver setup.** `tauri-driver` with `--native-driver` pointing at an `msedgedriver` whose version matches the runner's WebView2 runtime (resolved at job time; never a hard-coded version that drifts).
2. **Per-scenario isolation on Windows.** `fresh-app.ts` is Linux-only. On Windows, app data lives under the Roaming/Local AppData `org.qsp.qspider` dirs, and WebView2 data under Local AppData `…\EBWebView`. Those are Known Folders, so env overrides may not move them. The builder decides the mechanism (for example: end the session, wait for the app and its WebView2 processes to exit by PID tree, empty those dirs). The CI runner is ephemeral, so deleting the app's own dirs there is safe. **Never kill processes by name.**
3. **Native file dialog via UI Automation**, behind the same `openGameFile` / `pickFileInNativeDialog` contract: no scenario changes. Same rules as the AT-SPI driver: no keystrokes into whatever has focus, no dependence on UI language, set the path through the file-name edit's value pattern, confirm, verify that the dialog closed, a bounded kill timeout, and failures surface as `Native file dialog: …`. Builder picks the implementation (PowerShell + `System.Windows.Automation`, or a Python UIA library installed in the job), preferring nothing to install.
4. **Prereq check** already knows Windows (`prereqs.ts`: `win32: ['tauri-driver', 'msedgedriver']`, Linux probes only on Linux). Verify on the runner; extend only if it misses something.
5. **Runner** (`run-desktop-e2e.mjs`) already skips the private session off Linux and runs `wdio` directly with `shell: true` on Windows. Add only what the isolation from item 2 needs.
6. CI job `e2e-desktop-windows` (`checks.yml`), with failure artifacts uploaded the same way as the Linux job.

### Expected Windows-specific failures, and how to treat them

- Paths: backslashes, drive letters, case-insensitive file system vs. `game_uri.rs` per-segment lookup, `?query` stripping. Real defects → fix (red, then fix), ask first if player-visible.
- Origin: WebView2 serves the app from `http(s)://tauri.localhost`, not `tauri://localhost`. Storage, resource URLs and `isExternalUrl` may behave differently → defects, same rule.
- Chromium vs. WebKit in the desktop shell: some `webOnly` / `desktopOnly` splits encode WebKit quirks, not "desktop" behaviour. Builder may introduce a per-engine split if needed, with a stated reason; scenario text is unchanged.
- The relaunch flake (#167, absorbed by `specFileRetries: 2`) is WebKitWebDriver-specific; on Windows a retry needs its own documented cause.

### Working without local Windows

- Expect several CI rounds. To keep them cheap: a manual-dispatch (`workflow_dispatch`) input to run a single spec on Windows, and the job uploads the tauri-driver/app logs and the failure artifacts on every failure.
- The maintainer gets a short status line per CI round, not silence.
- The plan for PR 3 should front-load the infrastructure (driver, isolation, dialog, one core-flow scenario green) before turning on the full suite, and record each Windows-specific finding in the inventory "Suspected defects" list.

## Decided by the maintainer (this session)

- Phase 3 = standalone, then macOS, then Windows; one PR each.
- Standalone depth: the five checks under PR 1, on web and desktop-standalone.
- Desktop-standalone built through the real author pipeline (`qspider.desktop.json` → `standalone:config` → `tauri build`).
- Standalone CI runs as separate jobs alongside the existing ones (in parallel), not appended to them.
- macOS smoke loads a real game (startup → game running → first location text), for the main player and standalone.
- macOS trigger: desktop-relevant paths on PRs, always on `main` and weekly; required with skipped = pass.
- Windows trigger: every PR, required.
- E2E builds never use the repo's `public/game/` (the maintainer uses it locally).
- Windows: full desktop suite.
- No local Windows/macOS: GitHub Actions only.

## Claude's calls (check these)

- Standalone startup marker: a hidden data attribute set after `init()` finishes.
- A new standalone fixture game whose `game.cfg` lists two games (proves the first one starts).

- Standalone E2E builds stage their own public dir, selected by an E2E-only env var in the standalone Vite config.
- Sharding the Windows suite across parallel jobs.
- The macOS marker channel must also work on Linux, so it can be developed locally.
